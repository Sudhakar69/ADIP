Azure networking at enterprise scale

"Manage complex Azure Networking: Hub & Spoke, Virtual WAN, Application Gateway WAF, Private Link, and ExpressRoute." This is where most architect interviews go deepest — draw the topology, then defend every hop.

Hub & spoke topology

The default enterprise pattern: shared services centralized, workloads isolated.

// key rule interviewers check for: spokes route to each other through the hub firewall via UDRs — they do not peer directly.

Hub & spoke vs. Virtual WAN

Hub & Spoke (manual)Virtual WAN
ManagementYou build and peer every hub/spoke yourselfMicrosoft-managed backbone; hubs are a managed resource
ScalePeering limits and manual UDR maintenance get complex past a handful of regionsBuilt for many regions/branches — any-to-any routing is automatic
Branch connectivityYou configure VPN/ExpressRoute per hubNative integration for SD-WAN/branch sites at scale
Best forSimpler estates, full control over routing/firewall placementGlobal orgs with many regions, branches, or M&A-driven growth

Incident queue — Networking

NET-701SEV-1A workload in Spoke A can't reach a database in Spoke B. Both VNets are peered to the hub. Diagnose it.▶
  • Peering to the hub does not transitively connect spokes — confirm there's a User Defined Route (UDR) on each spoke's subnet sending 0.0.0.0/0 (or the specific spoke CIDR) via the hub firewall's private IP as next hop.
  • Check the firewall's own rules (network/application rule collections) actually allow that spoke-to-spoke flow — a UDR routes traffic to the firewall, it doesn't permit it.
  • Check NSGs on both source and destination subnets for the specific ports.

Resolution

Add/fix the UDR forcing spoke traffic through the hub NVA/firewall, and add an explicit allow rule on the firewall for that flow — this two-part check (routing exists + is permitted) is the core hub-spoke troubleshooting pattern.

NET-702SEV-2Users report intermittent slow responses only for traffic coming through the Application Gateway WAF. How do you isolate whether it's the WAF or the backend?▶
  • Check Application Gateway backend health probes and metrics — is latency added at the gateway hop itself, or is the backend genuinely slow and the gateway is just the entry point you happen to be measuring from?
  • Check WAF logs for rule evaluation overhead or false-positive blocks causing retries.
  • Compare gateway-to-backend latency metric vs. client-to-gateway latency to isolate the segment.

NET-703SEV-2A storage account was moved behind Private Link but an on-prem application can no longer resolve its hostname. Why, and how do you fix it?▶

Private Link relies on a Private DNS Zone that resolves the storage account's public FQDN to its private IP — inside Azure. On-prem DNS servers don't automatically know about that private zone. Fix: conditional forwarder on the on-prem DNS server pointing the relevant zone (e.g. privatelink.blob.core.windows.net) to a DNS resolver inside the hub VNet (Azure DNS Private Resolver or a VM running as forwarder), so on-prem clients resolve to the private IP too.

dnstroubleshooting
NET-704SEV-3Explain Private Link vs. Service Endpoint — why would you choose the more complex one?▶

Service Endpoint keeps traffic on the Azure backbone and restricts a PaaS resource's firewall to specific VNet/subnets — but the resource still has a public IP/endpoint, just with network-level ACLs. Private Link injects a private IP for the resource directly into your VNet — no public endpoint exists for that connection at all, traffic never touches the public internet path, and it works across peered VNets, on-prem (via VPN/ExpressRoute), and even other tenants. Choose Private Link whenever "no public exposure, period" is a compliance requirement, not just "restricted by IP."

fundamentals
NET-705SEV-1The ExpressRoute circuit just went down. On-prem users can't reach Azure resources. What's your immediate action and what's the durable fix?▶

Immediate: confirm scope via Azure Service Health and the ExpressRoute circuit's provider-side status; if a Site-to-Site VPN gateway exists as backup, traffic should already be failing over automatically via BGP route priority — verify it did. If no backup path exists, that's the actual finding here. Durable fix: every production ExpressRoute circuit should have a VPN failover path (or a second circuit via a different peering location/provider for true redundancy) — a single circuit is a single point of failure, no matter how reliable the provider's SLA is.

NET-706SEV-2How do you expose an internal API to a partner company without putting it on the public internet?▶

Publish it as an Azure Private Link Service behind a Standard Load Balancer — the partner (with their own Azure tenant) creates a Private Endpoint in their VNet that connects to your service over the Microsoft backbone, with connection approval on your side. No public IP, no VPN/ExpressRoute needed between the two organizations, and you can revoke access instantly by rejecting/removing the connection.

designsecurity
NET-707SEV-2WAF is blocking a legitimate customer request as a false positive (e.g. flagged as SQL injection). How do you fix it without disabling protection broadly?▶

Check WAF logs for the specific matched rule ID, then add a scoped exclusion (specific rule + specific request attribute/parameter, e.g. exclude a rule only for one query-string parameter known to contain SQL-like text legitimately) rather than switching the WAF to Detection-only mode or disabling the whole rule set — that would remove protection for every other request, not just this false positive.

securitynetworking
NET-708SEV-3Why do spokes route through a central firewall instead of each having their own NAT/firewall to the internet?▶

Centralizing egress/ingress inspection gives one consistent policy surface, one place to see all north-south traffic logs for security monitoring, and avoids each application team configuring (and misconfiguring) their own firewall independently. The trade-off is the hub firewall becomes a shared dependency and potential bottleneck/single point of failure — mitigated by deploying it in a zone-redundant/HA SKU and sizing for aggregate spoke traffic, not per-spoke.

design
NET-709SEV-2You need to give 40 branch offices connectivity to Azure with minimal ongoing operational overhead. Hub & spoke or vWAN?▶

Virtual WAN — at 40 branches, manually managing VPN/ExpressRoute gateways, peerings, and routing tables per hub in a DIY hub-and-spoke becomes a full-time job and a common source of routing mistakes. vWAN's managed hubs give any-to-any transitive routing between branches and VNets out of the box, which is exactly the problem at this scale.

design
NET-710SEV-2A new NSG rule was deployed and now health probes to a VM's backend pool are failing intermittently in the Load Balancer.▶

Azure Load Balancer health probes originate from a special virtual IP (168.63.129.16) — a common mistake is an NSG rule that blocks it without realizing that's the platform's own probe source, not "an unknown IP" to lock down. Confirm the NSG still allows the AzureLoadBalancer service tag; if it was recently tightened to explicit IPs, that's very likely the regression.
