DevSecOps: shifting security left

"Drive DevSecOps best practices by integrating security checks, vulnerability scanning, and compliance into CI/CD pipelines." The interview wants to know exactly where each control sits in the pipeline and what it catches that the others don't.

Incident queue — DevSecOps

SEC-501SEV-1SCA finds a critical CVE in a transitive dependency used by 30 services. What's your rollout plan?▶
  • Confirm exploitability in your actual usage — not every CVE in a dependency is reachable code (a "reachability" check saves panic-fixing unaffected paths).
  • Prioritize by exposure: internet-facing services patch first, internal batch jobs later, on a defined timeline (e.g. critical = 24-48h).
  • Automate the bump via a shared base image or lockfile bot (Dependabot/Renovate) across all 30 repos instead of 30 manual PRs.

SEC-502SEV-2Developers are complaining the security scan gate blocks every single build with low-severity findings. How do you fix the process without weakening security?▶

Tune the gate to fail the build only on severity thresholds that matter (e.g. Critical/High block, Medium/Low report-only with a tracked backlog), and support suppression with an expiring, reviewed exception (not a silent ignore) for accepted-risk findings. A gate that blocks on everything trains developers to ignore it entirely — that's the real security failure.

pipelineprocess
SEC-503SEV-1An engineer accidentally pushed AWS/Azure credentials to a public repo. Walk through your response.▶
  • Rotate/revoke the credential immediately — assume it's compromised the second it's public, regardless of how quickly it's deleted.
  • Check cloud provider activity logs for any usage from unfamiliar IPs during the exposure window.
  • Purge from Git history as cleanup (not the primary control), and add automated secret-scanning as a pre-receive/push gate so this can't reach the remote again.

SEC-504SEV-2How do you prevent an unscanned or unsigned container image from ever reaching production, even if someone bypasses the pipeline?▶

Pipeline gates alone are advisory — someone with cluster access can still kubectl apply directly. The durable control is admission control in-cluster: an OPA/Gatekeeper or Kyverno policy that rejects any pod spec referencing an image without a valid signature (cosign/Notary) or from an untrusted registry, enforced by the cluster itself, not just by CI.

SEC-505SEV-3What's the difference between SAST and DAST, and why do you need both?▶

SAST reads source code without executing it — fast, catches issues early, but can't see runtime behavior (misconfigured auth middleware that only fails under real request flow) and has false positives from patterns that are actually safe in context. DAST attacks a running instance like a real attacker would — catches real exploitable issues (including config/deployment mistakes SAST can't see) but runs late (needs a deployed environment) and can't point to a line of code. Mature pipelines run both at different stages.

fundamentals
SEC-506SEV-2Compliance asks for an audit trail of every production change for the last 12 months. Where does that live in your setup?▶

Git history (who changed what code, reviewed by whom) + pipeline run logs (what was deployed, when, by which pipeline, approved by whom) + cloud activity logs (Azure Activity Log / Entra sign-in logs for who touched what resource directly) together form the trail. This is also the argument for "everything through pipelines, nothing manual" — manual portal changes are the audit gap.

compliance
SEC-507SEV-2How do you scan Infrastructure-as-Code itself for security misconfigurations before it's ever applied?▶

Static IaC scanners (tfsec, checkov, Terrascan) run against the plan/HCL in CI — catching things like public storage buckets, open NSG rules (0.0.0.0/0), missing encryption-at-rest, or overly broad IAM roles before apply ever runs. Pair with a policy-as-code gate (Sentinel/OPA on the plan JSON) to hard-block specific violations rather than just warn.

iacpipeline
SEC-508SEV-3Explain the "shift-left" concept to someone skeptical it's worth the friction.▶

Cost of fixing a vulnerability rises the later it's found — a bad pattern caught by SAST at commit time is a one-line fix by the author who just wrote it; the same issue found in production is an incident, a hotfix, possibly a breach disclosure. Shift-left isn't about adding gates for their own sake, it's about moving the same checks to the cheapest point to fix them — and pairing that with fast, low-friction tooling so it doesn't become a bottleneck itself.

strategy
SEC-509SEV-2A pentest finds a service account with far more permissions than it uses. How would your pipeline have caught this earlier?▶

Least-privilege drift like this is best caught by periodic automated IAM access reviews (who/what has access vs. what it actually calls, using cloud-native tools like Azure Defender for Cloud's permission recommendations or AWS IAM Access Analyzer) rather than pipeline scanning alone — this is a config/identity governance gap, and the fix is scoped roles defined and reviewed as code (Terraform-managed role assignments) so grants are visible and diffable in PRs, not created ad hoc in the portal.
