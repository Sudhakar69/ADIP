DR strategies compared

Pick the right one for a given RTO/RPO budget — this is a design conversation, not a memory test.

PatternRTORPOCostNotes
Backup & restoreHours+Hours (backup interval)$Cheapest; acceptable for non-critical systems
Pilot lightTens of minutesMinutes$$Core services running minimally in DR region, scale up on failover
Warm standbyMinutesSeconds–minutes$$$Scaled-down full replica running continuously in DR region

RTO = how long you can be down. RPO = how much data you can afford to lose. Interviewers want you to pick a pattern because it matches a stated RTO/RPO, not because it's the most advanced option.

Incident queue — Landing Zone, Migration & DR

LZ-601SEV-2A new application team wants their own subscription. What governance has to be in place before you hand it over?▶
  • Subscription placed under the correct management group so it inherits the right Azure Policy set (allowed regions, required tags, denied resource types) automatically.
  • RBAC baseline: platform team retains a break-glass/emergency access role; app team gets Contributor scoped to their resource groups, not the subscription root.
  • Budget/cost alert and a network connection back to the hub (peering or vWAN) provisioned via the same landing zone pipeline everyone else uses — no manual one-off setup.
governance
LZ-602SEV-1The primary Azure region for a critical app is having a major outage right now. Walk through failover.▶
  • Confirm the scope from the Azure Status page — regional vs. specific service impact.
  • If pre-built for active-active/warm-standby: shift traffic via Azure Front Door / Traffic Manager priority or weighted routing to the healthy region.
  • If backup-and-restore only: this is where RTO gets tested for real — restore from the most recent geo-redundant backup into the paired region and reconnect DNS.
  • Communicate status honestly against the documented RTO/RPO — this is exactly what those numbers were promised for.

Resolution

The senior signal here is having tested this failover before it was needed — a DR plan nobody has drilled is a hypothesis, not a plan.

LZ-603SEV-2You're migrating 200 VMware VMs to Azure. Outline your approach with Azure Migrate.▶
  • Discover: deploy the Azure Migrate appliance in the VMware environment to inventory VMs, dependencies, and utilization data.
  • Assess: right-size target Azure VM SKUs from actual utilization (not guesswork), estimate cost, flag readiness issues.
  • Replicate: agentless or agent-based replication of disks to Azure, with an initial full sync then delta syncs.
  • Test migrate: boot a copy in an isolated network to validate before cutover — never skip this step for anything business-critical.
  • Migrate (cutover): final delta sync, shut down source, boot in Azure — wave-based (grouped by dependency, not just alphabetically) to limit blast radius per wave.
migration
LZ-604SEV-3Difference between Azure Backup and Azure Site Recovery — when do you use which?▶

Azure Backup protects data — point-in-time recoverable snapshots for restoring lost/corrupted/deleted data, RPO measured in the backup interval (typically daily). Azure Site Recovery protects availability — continuous replication of entire VMs to another region so you can fail the whole workload over in minutes with a much tighter RPO. They're complementary, not alternatives: ASR gets you back up fast after a regional event, Backup gets you back to a clean point after corruption/ransomware/accidental deletion that ASR would faithfully replicate too.

fundamentals
LZ-605SEV-2Leadership wants "everything highly available" but the budget doesn't support full active-active everywhere. How do you push back constructively?▶

Tier applications by business criticality and get an explicit, signed-off RTO/RPO per tier — not every system needs the same protection, and paying for active-active on a low-traffic internal reporting tool is wasted spend that could fund proper protection for the payment system. Present the cost curve (backup-restore → pilot light → warm standby → active-active) against actual business impact per app so the trade-off is a business decision, not a guess.

strategy
LZ-606SEV-1A Terraform apply against the platform landing zone accidentally deleted a production management group's policy assignment. Blast radius?▶

Because policy inherits down the management group hierarchy, removing an assignment at that level can instantly change compliance/enforcement for every subscription beneath it — potentially opening previously-blocked resource types, regions, or unencrypted storage across the whole estate. Immediate response: reapply the policy assignment (it should be in version control — reapply from Git, don't hand-recreate it), then audit what was created in the gap window using Azure Policy compliance state and Activity Log.

LZ-607SEV-2How do you decide between a multi-subscription vs. single large subscription design?▶

Multi-subscription is the enterprise-scale default: subscriptions are the hard boundary for RBAC, policy, and — critically — many Azure resource quotas/limits. Separating by environment (prod/non-prod) and/or business unit contains blast radius (a mistake in dev can't touch prod's subscription-level RBAC) and avoids hitting shared quota ceilings. Single subscription is only reasonable for genuinely small estates where the operational overhead of managing many subscriptions isn't yet justified.

design
LZ-608SEV-2Log Analytics costs have tripled in three months with no corresponding growth in workloads. Investigate.▶

Check ingestion volume by table/source (Usage solution query) — common culprits: a verbose diagnostic setting (e.g. AllLogs on a chatty resource) enabled during troubleshooting and never turned back down, a new NSG flow log or firewall log source added without a retention/sampling plan, or duplicate diagnostic settings sending the same data twice. Fix with per-table retention tuning, sampling for high-volume/low-value logs, and a cost-per-workspace alert to catch the next spike early.

costobservability
LZ-609SEV-3Define "landing zone" in one sentence you'd give a non-technical stakeholder.▶

A landing zone is the pre-built, pre-governed environment a new application "lands" into — networking, identity, security, and policy already wired up correctly — so teams start building on day one instead of re-solving governance from scratch every time.

communication
LZ-610SEV-2A DR failover test reveals the DR region's app version is three releases behind production. What process gap does that expose?▶

DR isn't a one-time build — it needs to be part of the standard deployment pipeline (deploy to both regions, or keep DR's image/config in lockstep automatically) and tested on a schedule, not just built once and assumed to stay current. Treat "DR region deploy" as a required pipeline stage, and run failover drills (game days) regularly enough that drift like this is caught in a drill, never in a real incident.
