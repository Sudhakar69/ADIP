Kubernetes

K8S-101SEV-1A pod keeps restarting in CrashLoopBackOff. Walk me through your diagnosis.▶

Diagnose

  • kubectl get pods -o wide — confirm restart count and node placement.
  • kubectl describe pod <pod> — check the Events section and last termination reason/exit code.
  • kubectl logs <pod> --previous — the crashed container's logs, not the new attempt.
  • Exit code 1 = app error; 137 = SIGKILL, almost always OOMKilled; 143 = SIGTERM, graceful shutdown didn't finish in time.

Resolution

Match the exit code to a cause: bad config/env var → fix and redeploy; OOMKilled → raise resources.limits.memory or fix a leak; failing liveness probe → the app is up but the probe path/port/timing is wrong, not the app itself.

Pitfall

Candidates jump straight to "increase the memory limit" without reading --previous logs first — that's guessing, not diagnosing. Always show the evidence before the fix.

workloadstroubleshooting
K8S-102SEV-2A new image was pushed but the deployment shows ImagePullBackOff.▶

Diagnose

  • kubectl describe pod Events will show the exact error: unauthorized, manifest unknown, or timeout.
  • Unauthorized → registry auth (imagePullSecrets) missing, expired, or not attached to the ServiceAccount.
  • Manifest unknown → tag doesn't exist (typo, or CI pushed to the wrong repo/tag).
  • Timeout → node can't reach the registry — check egress/firewall or private endpoint for ACR.

Resolution

For AKS + ACR, prefer az aks update --attach-acr (grants AcrPull via managed identity) over long-lived pull secrets — removes an entire class of "secret expired" incidents.

workloadsregistry
K8S-103SEV-1One node shows NotReady and its pods are stuck. What's your response?▶

Diagnose

  • kubectl describe node <node> — check Conditions: MemoryPressure, DiskPressure, PIDPressure, kubelet heartbeat age.
  • kubectl get events --field-selector involvedObject.name=<node> for kubelet/network plugin errors.
  • If it's a cloud VM, check the VMSS instance health in the Azure portal — could be an underlying host issue.

Resolution

If the node is unrecoverable within your SLA: kubectl cordon to stop new scheduling, kubectl drain --ignore-daemonsets --delete-emptydir-data to evict workloads safely (respecting PodDisruptionBudgets), then let Cluster Autoscaler or the node pool replace it. Never force-delete a node with stateful pods still attached to PVCs without confirming failover.

Pitfall

Draining without --ignore-daemonsets hangs forever since DaemonSet pods aren't meant to be evicted. Draining without checking PDBs can violate your own availability guarantees mid-incident.

cluster-admintroubleshooting
K8S-104SEV-2CPU usage is high but HPA never scales the deployment. Why?▶

Diagnose

  • kubectl describe hpa — check the "current/target" metrics line; if it shows <unknown>, metrics-server isn't reporting.
  • Confirm the deployment has resources.requests.cpu set — HPA's percentage math is usage ÷ request, no request means no baseline.
  • Check maxReplicas hasn't already been hit, and that the node pool has room (Cluster Autoscaler may itself be the bottleneck).

Resolution

Set explicit requests, confirm metrics-server/Prometheus adapter is healthy, and separate the two questions "did HPA decide to scale" (control plane) from "could the cluster fit the new pods" (capacity).

autoscaling
K8S-105SEV-2A pod is stuck in Pending with a PersistentVolumeClaim.▶

Diagnose

  • kubectl describe pvc and kubectl describe pod — Events usually say exactly why: no matching StorageClass, zone mismatch, or quota exceeded.
  • In AKS, a classic case: the PVC's disk was provisioned in zone-1 but the pod got scheduled to a node in zone-2 (zonal Azure Disks aren't portable across zones).

Resolution

Use a StorageClass with volumeBindingMode: WaitForFirstConsumer so the disk is provisioned in the same zone the scheduler actually picks, instead of provisioning immediately and hoping.

storage
K8S-106SEV-1Traffic to a Service returns intermittent 502s through the ingress. Where do you look?▶

Diagnose

  • Confirm kubectl get endpoints <svc> lists healthy pod IPs — a Service with a correct selector but zero endpoints is invisible traffic-wise.
  • Check the readiness probe: a pod can be Running but not Ready, and Ready is what gates Service endpoint membership.
  • Check ingress controller logs for upstream connection resets — often a mismatch between the app's actual listening port and the Service's targetPort.
  • Intermittent (not constant) 502s during deploys usually mean pods are removed from the endpoint list after traffic stops routing, not before — a missing preStop hook / graceful shutdown gap.

Resolution

Add a preStop sleep (or handle SIGTERM) so the pod keeps serving briefly while it's deregistered from the Service/ingress, and tune terminationGracePeriodSeconds. This is the single most common cause of "502s only during deploys."

Pitfall

Blaming the ingress controller first. In practice it's almost always readiness/endpoint timing, not the controller itself.

networkingtroubleshooting
K8S-107SEV-2Two pods in different namespaces can't reach each other after a NetworkPolicy rollout.▶

Diagnose

  • NetworkPolicies are additive and default-deny-once-selected: the moment any policy selects a pod, all traffic not explicitly allowed is denied.
  • Check both directions — ingress policy on the destination pod and egress policy on the source pod, both must allow the flow (if egress policies exist at all).
  • Cross-namespace traffic needs a namespaceSelector in the policy, not just a podSelector.

Resolution

Add an explicit allow rule with both podSelector and namespaceSelector (with a namespace label) for the calling service, and verify with a temporary kubectl run debug pod plus curl/nc rather than guessing from YAML alone.

networkingsecurity
K8S-108SEV-2A CI service account gets Forbidden: User cannot patch deployments. Fix it the right way.▶

Diagnose

  • kubectl auth can-i patch deployments --as=system:serviceaccount:ci:deployer -n prod reproduces the exact check.
  • Inspect the bound Role/ClusterRole and RoleBinding — missing verb, wrong resource, or bound in the wrong namespace.

Resolution

Grant least privilege with a namespaced Role + RoleBinding scoped to exactly the verbs needed (get, list, patch on deployments), not a blanket ClusterRoleBinding to cluster-admin just to unblock the pipeline.

Pitfall

"Just give it cluster-admin" is the answer that fails you in a security-conscious interview. Always narrate the least-privilege alternative even under time pressure.

securityrbac
K8S-109SEV-3A helm upgrade went out broken. How do you recover, and how could it have been caught earlier?▶

Diagnose

  • helm history <release> to see revisions, helm rollback <release> <revision> to revert immediately.
  • Post-recovery: helm diff upgrade (plugin) or --dry-run --debug in CI before every real upgrade to preview the rendered manifest diff.

Resolution

Roll back first, root-cause second — restoring service takes priority over understanding why in a live incident. Then add a CI gate: template-render + kubeval/conftest policy check + canary/staged rollout (Argo Rollouts or a manual weighted step) before full production.

helmdeployment
K8S-110SEV-3How do you upgrade a production AKS cluster's Kubernetes version with zero downtime?▶

Diagnose & approach

  • Upgrade control plane first (managed by Azure for AKS), then node pools — never skip more than one minor version at a time.
  • Use a surge upgrade setting (maxSurge) so AKS adds new nodes on the target version before draining old ones, instead of upgrading in place.
  • Confirm PodDisruptionBudgets exist for every critical workload so the drain respects minimum availability.

Resolution

Blue/green the node pool: create a new node pool on the target version, cordon+drain the old one gradually, delete it once traffic has fully shifted. This avoids any in-place node reboot risk entirely and gives an instant rollback path (just stop draining).

K8S-111SEV-2When would you choose a StatefulSet over a Deployment, and what breaks if you get it wrong?▶

Answer

  • Deployment: identical, interchangeable, stateless replicas — pod identity doesn't matter, any replica can serve any request.
  • StatefulSet: stable network identity (pod-0, pod-1...), stable per-pod storage (PVC follows the pod on reschedule), ordered start/stop — needed for databases, Kafka, etcd-like systems.

Pitfall

Running a clustered database as a plain Deployment with a shared PVC: on rescheduling, two pods can mount (or fight over) the same volume, or lose their identity, corrupting cluster state. This is a favorite "why is this wrong" whiteboard question.

workloads
K8S-112SEV-2Nodes are running hot and you suspect noisy-neighbor pods. How do you confirm and contain it?▶

Diagnose

  • kubectl top pods --all-namespaces --sort-by=cpu for a quick view; Grafana/Prometheus for historical confirmation.
  • Check whether offending pods have limits set at all — without limits a pod can consume all available node CPU/memory.

Resolution

Enforce ResourceQuota at the namespace level and LimitRange for default requests/limits so no team can omit them; consider taints/tolerations or separate node pools to isolate genuinely bursty workloads from latency-sensitive ones.

cluster-admincapacity
K8S-113SEV-1etcd is corrupted / the control plane is unresponsive. What's the recovery plan?▶

Approach

  • On managed AKS, the control plane (including etcd) is Azure-operated — your job is opening a support case and failing over workloads, not restoring etcd yourself.
  • For self-managed clusters: etcd should have scheduled snapshots (etcdctl snapshot save); restore replaces the data directory on each member and requires a coordinated cluster restart.

Resolution

This question is really testing whether you know etcd is the cluster's single source of truth, so its backup cadence and restore drill needs to be tested regularly, not just configured and forgotten — and that on AKS this is Microsoft's responsibility under the shared responsibility model.

cluster-admindisaster-recovery
K8S-114SEV-3How do you secure a production cluster end to end — give me the layers.▶

Answer — layer by layer

  • Cluster access: Entra ID integration for kubectl auth, RBAC with least privilege, no shared static kubeconfigs.
  • Workload identity: Azure AD Workload Identity / Managed Identity instead of embedding cloud credentials as Secrets.
  • Network: default-deny NetworkPolicies, private cluster (no public API server endpoint) where possible.
  • Supply chain: image scanning in CI, signed images, admission control (e.g. Gatekeeper/Kyverno) to block unscanned or non-compliant images.
  • Runtime: Pod Security Admission (restricted profile), read-only root filesystem, non-root users, dropped Linux capabilities.
  • Secrets: external secret store (Key Vault via CSI driver) instead of raw Kubernetes Secrets at rest.

CI/CD & Git

CI-201SEV-1A pipeline that worked yesterday fails today with no code changes. First three things you check?▶
  • Runner/agent health — did the runner pool change, get drained, or hit a version bump?
  • External dependency drift — base image, package registry, or a floating tag (:latest) that moved underneath you.
  • Pipeline/config changes merged by someone else, or a CI/CD variable that expired (token, secret rotation).

Resolution

Pin versions everywhere — base images by digest, tool versions explicitly — so "nothing changed" is actually true and the pipeline is reproducible.

# .gitlab-ci.yml (excerpt) deploy_prod: stage: deploy environment: name: production url: https://app.example.com when: manual rules: - if: '$CI_COMMIT_BRANCH == "main"' needs: ["deploy_staging"]

Combine when: manual with GitLab protected environments so only specific users/groups can click "deploy," plus branch rules so it can't fire from a feature branch.

CI-203SEV-1A bad deploy just went to production. What's your rollback strategy, and how fast can you execute it?▶
  • Fastest: re-run the previous successful pipeline's deploy job — the artifact/image already exists, no rebuild needed.
  • For Kubernetes: kubectl rollout undo or helm rollback as an even faster path if the pipeline re-run is slow.
  • For infra/config changes: revert the commit (not just redeploy old code) so the repo stays the single source of truth — avoids future drift between "what's deployed" and "what's in Git."

Resolution

State a target: "rollback executes in under 5 minutes because we redeploy a known-good, already-built artifact rather than rebuilding." That specific, measurable answer is what separates senior from mid-level here.

CI-204SEV-2Pipelines are slow — a build that used to take 4 minutes now takes 20. How do you speed it up?▶
  • Enable/verify layer caching (Docker build cache, GitLab cache: keyed by lockfile hash) — most slowdowns are cache invalidation, not raw compute.
  • Parallelize independent jobs (test splitting/matrix) instead of one long serial stage.
  • Check runner autoscaling — are jobs queued waiting for an available runner rather than actually running slow?

CI-205SEV-2Two engineers force-pushed over each other's work on a shared branch. How do you prevent this?▶
  • Branch protection: disallow force-push and direct commits to main/release/*.
  • Require merge requests with at least one approval and a passing pipeline before merge (merge trains for high-contention repos).

CI-206SEV-3Explain GitLab CI/CD variables and secret handling — how do you avoid leaking a secret in logs?▶
  • Mark sensitive CI/CD variables as Protected (only exposed on protected branches/tags) and Masked (redacted from job logs).
  • Prefer external secret stores (Key Vault, HashiCorp Vault) with short-lived tokens over long-lived CI variables where possible.
  • Never echo a variable, avoid set -x in scripts that touch secrets, and treat any accidental log exposure as a rotation event, not just a log cleanup.

CI-207SEV-2You need the same pipeline logic reused across 30 microservice repos without copy-pasting YAML. How?▶

Centralize with GitLab CI/CD includes (include: project:) pointing at a shared templates repo, parameterized with variables per service. Update the template once, every consuming pipeline picks it up on next run — versus 30 repos drifting independently.

CI-208SEV-1Merge conflict on a critical hotfix branch, production is down, you need this merged in the next 5 minutes.▶

Stay calm and don't shortcut safety: pull latest target branch, resolve conflicts locally with full context of both changes (not blind "accept theirs"), run the fast/critical subset of tests locally if the full pipeline is too slow, push, and let CI gate the merge. If genuinely blocked by a slow pipeline, use a documented emergency-deploy process (still logged, still reviewed after the fact) rather than disabling checks silently — traceability matters even in a fire.

CI-209SEV-3What's the difference between continuous delivery and continuous deployment, and which would you recommend here?▶

Continuous delivery: every change is automatically built, tested, and made release-ready, but a human decides when it actually ships (manual gate to prod). Continuous deployment: every change that passes the pipeline goes live automatically, no human gate. Recommendation depends on blast radius and rollback speed — teams with strong automated testing, feature flags, and fast rollback can safely run continuous deployment; regulated or high-risk-change environments usually keep a manual approval step for delivery instead.

CI-210SEV-2A GitLab runner has intermittent network failures pulling dependencies mid-pipeline. Long-term fix?▶

Add retry logic for network-flaky steps (GitLab supports retry: per job), but the durable fix is a local artifact/package proxy (e.g. a pull-through cache for npm/pip/Maven, or ACR as a pull-through cache for base images) so builds don't depend on the public internet's availability at all.

pipelinereliability
CI-211SEV-2How do you version and promote a build artifact across dev → staging → prod without rebuilding it each time?▶

Build once, tag with an immutable identifier (commit SHA or semantic version + SHA), push to a registry, then each environment's deploy job references that exact tag/digest. Promotion between environments becomes "point staging's deployment at the same digest that passed dev," never a rebuild — guaranteeing what you tested is exactly what ships.

Terraform & Ansible

IAC-301SEV-1Two engineers ran terraform apply at the same time and the state file is now corrupted. What happened, and how do you prevent it?▶

Without a remote backend + locking, concurrent applies can both read the same state, make conflicting writes, and the last write wins — silently dropping the other's changes or leaving orphaned resources. Fix going forward: remote state in Azure Storage with native locking, and force all applies through CI/CD (no local applies against shared state) so there's only ever one writer.

Recovery

Terraform Storage backend keeps state versioning — restore the last known-good version from blob snapshot history, then reconcile with a fresh plan to see what's actually drifted before touching anything.

stateincident
IAC-302SEV-2terraform plan wants to destroy and recreate a production database. Nothing in the code looks like it should change that. Why?▶

Classic causes: a change to an immutable attribute (some arguments force replacement, not update-in-place — check the provider docs for ForceNew/"requires replacement"), a provider version bump that changed a default, or someone edited the resource out-of-band so Terraform's plan is "correcting" drift in the most destructive way possible.

Resolution

Never trust a destructive plan blindly on stateful resources — read the plan's "forces replacement" reason line by line, and for genuinely risky resources use lifecycle { prevent_destroy = true } as a guardrail.

Pitfall

Running apply without reading the plan output in a live interview scenario is an instant red flag — always narrate "I'd read the plan first."

terraformtroubleshooting
IAC-303SEV-2How do you structure Terraform for dev/staging/prod — workspaces, or separate state per environment?▶

Prefer separate state files per environment (via separate directories/backends, or a module + tfvars per env) over Terraform workspaces for prod-grade separation — workspaces share the same backend config and code path, which makes it too easy for a mistake in one workspace to bleed into another. Reusable modules + per-environment variable files give the same DRY-ness with a harder blast-radius boundary.

terraformstructure
IAC-304SEV-2A secret (client secret / connection string) got committed into a Terraform file. What now?▶
  • Rotate the secret immediately — removing it from Git history does not undo exposure, treat it as compromised.
  • Purge it from Git history (git filter-repo / BFG) as a secondary cleanup step, not the primary fix.
  • Long-term: pull secrets from Key Vault via a data source at plan/apply time, add pre-commit secret scanning, and mark sensitive Terraform variables with sensitive = true so they're redacted from CLI/plan output.
securityterraform
IAC-305SEV-3Write the shape of a reusable Terraform module for an AKS cluster. What goes in, what comes out?▶
# modules/aks/variables.tf variable "cluster_name" { type = string } variable "node_count" { type = number, default = 3 } variable "vnet_subnet_id" { type = string } # modules/aks/outputs.tf output "cluster_id" { value = azurerm_kubernetes_cluster.this.id } output "kube_config" { value = azurerm_kubernetes_cluster.this.kube_config_raw, sensitive = true } output "identity_principal_id" { value = azurerm_kubernetes_cluster.this.identity[0].principal_id }

Inputs are the things that legitimately vary per environment; outputs are what other modules (networking, IAM role assignments) need to wire up next — this is what makes modules composable instead of copy-pasted.

terraformmodules
IAC-306SEV-2An Ansible playbook run is not idempotent — running it twice changes things the second time too. How do you fix it?▶

Usually caused by using shell/command modules for tasks that have a proper idempotent module (e.g. shell: apt-get install nginx instead of the apt module, which checks state first). Fix: use resource-oriented modules wherever they exist, and for genuine shell steps add creates:/changed_when: conditions so Ansible can correctly report "no change needed."

ansible
IAC-307SEV-2Terraform apply is taking 40 minutes for a plan with 15 resources. What would you investigate?▶
  • Cloud API rate limiting/throttling on the provider — check for 429s in verbose (TF_LOG=DEBUG) output.
  • Resources with genuinely slow provisioning (e.g. AKS cluster creation, VPN gateways) vs. resources stuck due to a dependency misconfiguration.
  • Unnecessary serialization — resources that could apply in parallel but are chained by an implicit dependency (e.g. referencing an unrelated attribute just to force ordering).
terraformperformance
IAC-308SEV-1You need to bring an existing, manually-created production VNet under Terraform management without downtime. Approach?▶

Write the Terraform resource block matching the existing resource's configuration, then terraform import its Azure resource ID into state, and immediately run plan — a clean "no changes" plan confirms your code accurately matches reality. Iterate on the code (not the live resource) until the plan is empty before ever running apply, so the first real apply makes zero changes.

terraformmigration
IAC-309SEV-2How do you test infrastructure code before it ever reaches production?▶
  • terraform validate + fmt -check in CI for syntax/style.
  • Static policy checks (tfsec, checkov, or Sentinel/OPA) to catch insecure configs (open NSGs, public storage) before apply.
  • terraform plan posted as a CI comment on the merge request for human review — the diff is the review.
  • Apply to a real short-lived sandbox/staging subscription for higher-risk modules before prod.
terraformdevsecops
IAC-310SEV-3When would you choose Bicep over Terraform for Azure, given both are in scope for this role?▶

Bicep is Azure-native (compiles to ARM), gets day-one support for brand-new Azure resource types, and needs no state file — Azure Resource Manager itself is the source of truth. Terraform is cloud-agnostic, has a larger module ecosystem, and is the better choice in multi-cloud or hybrid estates, or where the org has existing Terraform investment. In an Azure-only shop with a small platform team, Bicep reduces operational surface area (no state backend to manage); in a mixed-cloud org, Terraform's one tool for everything usually wins.

Monitoring & Incident Response

MON-401SEV-1Production is down. You get paged. What are your first five minutes?▶
  • Acknowledge the page (stop it re-escalating) and open the relevant dashboard — don't start guessing from memory.
  • Confirm blast radius: one region, all regions, one service, or a shared dependency (DNS, auth, database)?
  • Declare an incident with a severity and, if the org has one, an incident commander role — communication starts now, not after you've found root cause.
  • Look for what changed recently: deploys, config, feature flags, infra changes in the last few hours — most incidents trace back to a recent change.

Resolution

Mitigate first: rollback, feature-flag off, or scale up/failover — restore service before you fully understand why. Root cause analysis happens after the fire is out.

incidentprocess
MON-402SEV-2Your team is getting paged 40 times a week and burning out. How do you fix alerting, not just tolerance for pages?▶
  • Audit every alert: does it map to actual user-facing impact (SLO burn rate), or is it a raw resource threshold (CPU > 80%) that's frequently noisy and not actionable?
  • Convert "page-worthy" to symptom-based alerts (error rate, latency, availability) and demote cause-based signals (disk 70% full) to tickets/dashboards, not pages.
  • Add alert grouping/deduplication and sensible for-durations so one blip doesn't fire five pages.

Resolution

Every alert should be actionable and tied to user impact. If an alert fires and the response is "nothing to do," it shouldn't be a page.

MON-403SEV-3Define SLI, SLO, and error budget, and how they change your deploy decisions.▶
  • SLI (indicator): a measured metric, e.g. "% of requests under 300ms."
  • SLO (objective): a target for that SLI, e.g. "99.9% of requests under 300ms over 30 days."
  • Error budget: the allowed 0.1% — once it's spent, the team's priority shifts from shipping features to reliability work, and risky deploys get paused or gated behind extra review.

MON-404SEV-1Prometheus itself is down / not scraping — you're flying blind during an incident. What do you do?▶

Fall back to secondary signals: cloud provider platform metrics (Azure Monitor), application logs directly, or a synthetic uptime check that's independent of your primary stack. This is also the argument for why monitoring infrastructure itself needs redundancy/HA and shouldn't share a failure domain with what it's monitoring — e.g. don't run your only Prometheus inside the same cluster it's the sole observer of, without a secondary path.

MON-405SEV-2Walk me through writing a blameless postmortem after a major outage.▶
  • Timeline of objective facts: when it started, when detected, when mitigated, when resolved — timestamps, not opinions.
  • Impact: quantify it (users affected, revenue, SLO burn) rather than "it was bad."
  • Root cause via 5 Whys, focused on systems and process gaps, never on naming/blaming an individual.
  • Action items: specific, owned, dated, and tracked to closure — a postmortem with no completed action items is theater.
i

Language matters: "the deploy process allowed an unvalidated config to reach prod," not "Dave pushed bad config." Interviewers listen for this framing specifically.

MON-406SEV-2Disk usage on a node is climbing steadily and will hit 100% in 6 hours. How do you handle it — page now or wait?▶

This is a textbook case for a warning-level alert with a longer response window, not a page — it's predictable and not yet impacting users. Route it to a ticket/Slack channel with a clear runbook (log rotation, old artifact cleanup, or scale storage), and only escalate to a page if the trend accelerates or crosses a near-term threshold (e.g. <1 hour to full).

MON-408SEV-2Latency degraded slowly over two weeks, no single deploy caused it, and nobody noticed until customers complained. What failed?▶

The alerting was threshold-based on a moving baseline that crept along with the degradation ("boiling frog" problem), or there was no SLO-based burn-rate alert at all — only "is it fully down" checks. Fix: alert on rate of change and on absolute SLO thresholds together, and review trend dashboards on a regular cadence, not only reactively.

MON-409SEV-1During an active outage, three engineers are independently trying different fixes and stepping on each other. What's wrong with the response and how do you fix it live?▶

Missing incident command structure. Assign a single Incident Commander who coordinates and makes the final call on which mitigation to try (and in what order), a dedicated communications channel/thread for status updates, and route all changes through the IC so actions aren't taken in parallel without visibility. This is a process question as much as a technical one — seniority shows in recognizing coordination failure as the actual root cause.

MON-410SEV-2How do you monitor a Kubernetes cluster itself, separate from the applications running on it?▶

MON-412SEV-3How do you balance "move fast" with "keep things reliable" — the JD literally asks for this balance.▶

Error budgets are the concrete mechanism: as long as the budget isn't exhausted, teams ship freely; once it is, velocity yields to reliability work automatically, by policy rather than by argument. Pair that with progressive delivery (canary/feature flags) so "moving fast" doesn't mean "betting the whole fleet on every change" — blast radius is controlled independently of release frequency.

DevSecOps

SEC-501SEV-1SCA finds a critical CVE in a transitive dependency used by 30 services. What's your rollout plan?▶
  • Confirm exploitability in your actual usage — not every CVE in a dependency is reachable code (a "reachability" check saves panic-fixing unaffected paths).
  • Prioritize by exposure: internet-facing services patch first, internal batch jobs later, on a defined timeline (e.g. critical = 24-48h).
  • Automate the bump via a shared base image or lockfile bot (Dependabot/Renovate) across all 30 repos instead of 30 manual PRs.

SEC-502SEV-2Developers are complaining the security scan gate blocks every single build with low-severity findings. How do you fix the process without weakening security?▶

Tune the gate to fail the build only on severity thresholds that matter (e.g. Critical/High block, Medium/Low report-only with a tracked backlog), and support suppression with an expiring, reviewed exception (not a silent ignore) for accepted-risk findings. A gate that blocks on everything trains developers to ignore it entirely — that's the real security failure.

SEC-503SEV-1An engineer accidentally pushed AWS/Azure credentials to a public repo. Walk through your response.▶
  • Rotate/revoke the credential immediately — assume it's compromised the second it's public, regardless of how quickly it's deleted.
  • Check cloud provider activity logs for any usage from unfamiliar IPs during the exposure window.
  • Purge from Git history as cleanup (not the primary control), and add automated secret-scanning as a pre-receive/push gate so this can't reach the remote again.

SEC-504SEV-2How do you prevent an unscanned or unsigned container image from ever reaching production, even if someone bypasses the pipeline?▶

Pipeline gates alone are advisory — someone with cluster access can still kubectl apply directly. The durable control is admission control in-cluster: an OPA/Gatekeeper or Kyverno policy that rejects any pod spec referencing an image without a valid signature (cosign/Notary) or from an untrusted registry, enforced by the cluster itself, not just by CI.

supply-chainkubernetes
SEC-505SEV-3What's the difference between SAST and DAST, and why do you need both?▶

SAST reads source code without executing it — fast, catches issues early, but can't see runtime behavior (misconfigured auth middleware that only fails under real request flow) and has false positives from patterns that are actually safe in context. DAST attacks a running instance like a real attacker would — catches real exploitable issues (including config/deployment mistakes SAST can't see) but runs late (needs a deployed environment) and can't point to a line of code. Mature pipelines run both at different stages.

fundamentals
SEC-506SEV-2Compliance asks for an audit trail of every production change for the last 12 months. Where does that live in your setup?▶

Git history (who changed what code, reviewed by whom) + pipeline run logs (what was deployed, when, by which pipeline, approved by whom) + cloud activity logs (Azure Activity Log / Entra sign-in logs for who touched what resource directly) together form the trail. This is also the argument for "everything through pipelines, nothing manual" — manual portal changes are the audit gap.

compliance
SEC-507SEV-2How do you scan Infrastructure-as-Code itself for security misconfigurations before it's ever applied?▶

Static IaC scanners (tfsec, checkov, Terrascan) run against the plan/HCL in CI — catching things like public storage buckets, open NSG rules (0.0.0.0/0), missing encryption-at-rest, or overly broad IAM roles before apply ever runs. Pair with a policy-as-code gate (Sentinel/OPA on the plan JSON) to hard-block specific violations rather than just warn.

iacpipeline
SEC-508SEV-3Explain the "shift-left" concept to someone skeptical it's worth the friction.▶

Cost of fixing a vulnerability rises the later it's found — a bad pattern caught by SAST at commit time is a one-line fix by the author who just wrote it; the same issue found in production is an incident, a hotfix, possibly a breach disclosure. Shift-left isn't about adding gates for their own sake, it's about moving the same checks to the cheapest point to fix them — and pairing that with fast, low-friction tooling so it doesn't become a bottleneck itself.

strategy
SEC-509SEV-2A pentest finds a service account with far more permissions than it uses. How would your pipeline have caught this earlier?▶

Least-privilege drift like this is best caught by periodic automated IAM access reviews (who/what has access vs. what it actually calls, using cloud-native tools like Azure Defender for Cloud's permission recommendations or AWS IAM Access Analyzer) rather than pipeline scanning alone — this is a config/identity governance gap, and the fix is scoped roles defined and reviewed as code (Terraform-managed role assignments) so grants are visible and diffable in PRs, not created ad hoc in the portal.

Landing Zone, Multi-Region & DR

LZ-601SEV-2A new application team wants their own subscription. What governance has to be in place before you hand it over?▶
  • Subscription placed under the correct management group so it inherits the right Azure Policy set (allowed regions, required tags, denied resource types) automatically.
  • RBAC baseline: platform team retains a break-glass/emergency access role; app team gets Contributor scoped to their resource groups, not the subscription root.
  • Budget/cost alert and a network connection back to the hub (peering or vWAN) provisioned via the same landing zone pipeline everyone else uses — no manual one-off setup.

LZ-602SEV-1The primary Azure region for a critical app is having a major outage right now. Walk through failover.▶
  • Confirm the scope from the Azure Status page — regional vs. specific service impact.
  • If pre-built for active-active/warm-standby: shift traffic via Azure Front Door / Traffic Manager priority or weighted routing to the healthy region.
  • If backup-and-restore only: this is where RTO gets tested for real — restore from the most recent geo-redundant backup into the paired region and reconnect DNS.
  • Communicate status honestly against the documented RTO/RPO — this is exactly what those numbers were promised for.

Resolution

The senior signal here is having tested this failover before it was needed — a DR plan nobody has drilled is a hypothesis, not a plan.

LZ-603SEV-2You're migrating 200 VMware VMs to Azure. Outline your approach with Azure Migrate.▶
  • Discover: deploy the Azure Migrate appliance in the VMware environment to inventory VMs, dependencies, and utilization data.
  • Assess: right-size target Azure VM SKUs from actual utilization (not guesswork), estimate cost, flag readiness issues.
  • Replicate: agentless or agent-based replication of disks to Azure, with an initial full sync then delta syncs.
  • Test migrate: boot a copy in an isolated network to validate before cutover — never skip this step for anything business-critical.
  • Migrate (cutover): final delta sync, shut down source, boot in Azure — wave-based (grouped by dependency, not just alphabetically) to limit blast radius per wave.
migration
LZ-604SEV-3Difference between Azure Backup and Azure Site Recovery — when do you use which?▶

Azure Backup protects data — point-in-time recoverable snapshots for restoring lost/corrupted/deleted data, RPO measured in the backup interval (typically daily). Azure Site Recovery protects availability — continuous replication of entire VMs to another region so you can fail the whole workload over in minutes with a much tighter RPO. They're complementary, not alternatives: ASR gets you back up fast after a regional event, Backup gets you back to a clean point after corruption/ransomware/accidental deletion that ASR would faithfully replicate too.

fundamentals
LZ-605SEV-2Leadership wants "everything highly available" but the budget doesn't support full active-active everywhere. How do you push back constructively?▶

Tier applications by business criticality and get an explicit, signed-off RTO/RPO per tier — not every system needs the same protection, and paying for active-active on a low-traffic internal reporting tool is wasted spend that could fund proper protection for the payment system. Present the cost curve (backup-restore → pilot light → warm standby → active-active) against actual business impact per app so the trade-off is a business decision, not a guess.

strategy
LZ-606SEV-1A Terraform apply against the platform landing zone accidentally deleted a production management group's policy assignment. Blast radius?▶

Because policy inherits down the management group hierarchy, removing an assignment at that level can instantly change compliance/enforcement for every subscription beneath it — potentially opening previously-blocked resource types, regions, or unencrypted storage across the whole estate. Immediate response: reapply the policy assignment (it should be in version control — reapply from Git, don't hand-recreate it), then audit what was created in the gap window using Azure Policy compliance state and Activity Log.

governanceincident
LZ-607SEV-2How do you decide between a multi-subscription vs. single large subscription design?▶

Multi-subscription is the enterprise-scale default: subscriptions are the hard boundary for RBAC, policy, and — critically — many Azure resource quotas/limits. Separating by environment (prod/non-prod) and/or business unit contains blast radius (a mistake in dev can't touch prod's subscription-level RBAC) and avoids hitting shared quota ceilings. Single subscription is only reasonable for genuinely small estates where the operational overhead of managing many subscriptions isn't yet justified.

LZ-608SEV-2Log Analytics costs have tripled in three months with no corresponding growth in workloads. Investigate.▶

Check ingestion volume by table/source (Usage solution query) — common culprits: a verbose diagnostic setting (e.g. AllLogs on a chatty resource) enabled during troubleshooting and never turned back down, a new NSG flow log or firewall log source added without a retention/sampling plan, or duplicate diagnostic settings sending the same data twice. Fix with per-table retention tuning, sampling for high-volume/low-value logs, and a cost-per-workspace alert to catch the next spike early.

LZ-609SEV-3Define "landing zone" in one sentence you'd give a non-technical stakeholder.▶

A landing zone is the pre-built, pre-governed environment a new application "lands" into — networking, identity, security, and policy already wired up correctly — so teams start building on day one instead of re-solving governance from scratch every time.

communication
LZ-610SEV-2A DR failover test reveals the DR region's app version is three releases behind production. What process gap does that expose?▶

DR isn't a one-time build — it needs to be part of the standard deployment pipeline (deploy to both regions, or keep DR's image/config in lockstep automatically) and tested on a schedule, not just built once and assumed to stay current. Treat "DR region deploy" as a required pipeline stage, and run failover drills (game days) regularly enough that drift like this is caught in a drill, never in a real incident.

Azure Networking

NET-701SEV-1A workload in Spoke A can't reach a database in Spoke B. Both VNets are peered to the hub. Diagnose it.▶
  • Peering to the hub does not transitively connect spokes — confirm there's a User Defined Route (UDR) on each spoke's subnet sending 0.0.0.0/0 (or the specific spoke CIDR) via the hub firewall's private IP as next hop.
  • Check the firewall's own rules (network/application rule collections) actually allow that spoke-to-spoke flow — a UDR routes traffic to the firewall, it doesn't permit it.
  • Check NSGs on both source and destination subnets for the specific ports.

Resolution

Add/fix the UDR forcing spoke traffic through the hub NVA/firewall, and add an explicit allow rule on the firewall for that flow — this two-part check (routing exists + is permitted) is the core hub-spoke troubleshooting pattern.

NET-702SEV-2Users report intermittent slow responses only for traffic coming through the Application Gateway WAF. How do you isolate whether it's the WAF or the backend?▶
  • Check Application Gateway backend health probes and metrics — is latency added at the gateway hop itself, or is the backend genuinely slow and the gateway is just the entry point you happen to be measuring from?
  • Check WAF logs for rule evaluation overhead or false-positive blocks causing retries.
  • Compare gateway-to-backend latency metric vs. client-to-gateway latency to isolate the segment.

NET-703SEV-2A storage account was moved behind Private Link but an on-prem application can no longer resolve its hostname. Why, and how do you fix it?▶

Private Link relies on a Private DNS Zone that resolves the storage account's public FQDN to its private IP — inside Azure. On-prem DNS servers don't automatically know about that private zone. Fix: conditional forwarder on the on-prem DNS server pointing the relevant zone (e.g. privatelink.blob.core.windows.net) to a DNS resolver inside the hub VNet (Azure DNS Private Resolver or a VM running as forwarder), so on-prem clients resolve to the private IP too.

NET-704SEV-3Explain Private Link vs. Service Endpoint — why would you choose the more complex one?▶

Service Endpoint keeps traffic on the Azure backbone and restricts a PaaS resource's firewall to specific VNet/subnets — but the resource still has a public IP/endpoint, just with network-level ACLs. Private Link injects a private IP for the resource directly into your VNet — no public endpoint exists for that connection at all, traffic never touches the public internet path, and it works across peered VNets, on-prem (via VPN/ExpressRoute), and even other tenants. Choose Private Link whenever "no public exposure, period" is a compliance requirement, not just "restricted by IP."

fundamentals
NET-705SEV-1The ExpressRoute circuit just went down. On-prem users can't reach Azure resources. What's your immediate action and what's the durable fix?▶

Immediate: confirm scope via Azure Service Health and the ExpressRoute circuit's provider-side status; if a Site-to-Site VPN gateway exists as backup, traffic should already be failing over automatically via BGP route priority — verify it did. If no backup path exists, that's the actual finding here. Durable fix: every production ExpressRoute circuit should have a VPN failover path (or a second circuit via a different peering location/provider for true redundancy) — a single circuit is a single point of failure, no matter how reliable the provider's SLA is.

NET-706SEV-2How do you expose an internal API to a partner company without putting it on the public internet?▶

Publish it as an Azure Private Link Service behind a Standard Load Balancer — the partner (with their own Azure tenant) creates a Private Endpoint in their VNet that connects to your service over the Microsoft backbone, with connection approval on your side. No public IP, no VPN/ExpressRoute needed between the two organizations, and you can revoke access instantly by rejecting/removing the connection.

NET-707SEV-2WAF is blocking a legitimate customer request as a false positive (e.g. flagged as SQL injection). How do you fix it without disabling protection broadly?▶

Check WAF logs for the specific matched rule ID, then add a scoped exclusion (specific rule + specific request attribute/parameter, e.g. exclude a rule only for one query-string parameter known to contain SQL-like text legitimately) rather than switching the WAF to Detection-only mode or disabling the whole rule set — that would remove protection for every other request, not just this false positive.

NET-708SEV-3Why do spokes route through a central firewall instead of each having their own NAT/firewall to the internet?▶

Centralizing egress/ingress inspection gives one consistent policy surface, one place to see all north-south traffic logs for security monitoring, and avoids each application team configuring (and misconfiguring) their own firewall independently. The trade-off is the hub firewall becomes a shared dependency and potential bottleneck/single point of failure — mitigated by deploying it in a zone-redundant/HA SKU and sizing for aggregate spoke traffic, not per-spoke.

NET-709SEV-2You need to give 40 branch offices connectivity to Azure with minimal ongoing operational overhead. Hub & spoke or vWAN?▶

Virtual WAN — at 40 branches, manually managing VPN/ExpressRoute gateways, peerings, and routing tables per hub in a DIY hub-and-spoke becomes a full-time job and a common source of routing mistakes. vWAN's managed hubs give any-to-any transitive routing between branches and VNets out of the box, which is exactly the problem at this scale.

NET-710SEV-2A new NSG rule was deployed and now health probes to a VM's backend pool are failing intermittently in the Load Balancer.▶

SEC-801SEV-1A pipeline service principal has Owner on the whole subscription. Security flags it in an audit. How do you remediate without breaking the pipeline?▶
  • Inventory what the pipeline actually does — deploy to two resource groups, read from a storage account, write to a container registry.
  • Replace the broad Owner grant with scoped custom or built-in roles at the resource group level covering exactly those actions (e.g. Contributor on RG A/B, AcrPush on the registry).
  • Where possible, replace the service principal with a federated workload identity (OIDC trust between the CI system and Entra ID) so there's no long-lived client secret to leak at all.

Resolution

Scope the role down to least privilege per resource, migrate the credential to workload identity federation, and add an Azure Policy that denies new role assignments of Owner at subscription scope going forward so this doesn't quietly recur.

Pitfall

Removing Owner without first confirming every action the pipeline performs — you will find out what it needed the hard way, mid-incident, if you skip the inventory step.

rbacsecurity
SEC-802SEV-2An application VM needs to read secrets from Key Vault. Walk through the secure way to wire that up.▶

Enable a system-assigned Managed Identity on the VM. Grant that identity an RBAC role (e.g. Key Vault Secrets User) scoped to just that vault — not the older access-policy model, which is being phased out in favor of RBAC for Key Vault. The application code calls the Key Vault SDK, which silently obtains a token via the instance metadata endpoint — no connection string, no secret, ever lands in app config or environment variables. Rotate underlying secrets in the vault itself; the app always reads current values, so a secret rotation needs no app redeploy.

SEC-803SEV-2Explain PIM activation end to end for a scenario where an engineer needs 2 hours of Contributor access to fix a production issue at 11pm.▶
  • Engineer is pre-assigned as eligible (not active) for the Contributor role on the target scope.
  • At 11pm they open PIM and request activation: supply a justification, optionally require MFA re-confirmation, and set a duration up to the policy's max (say, 4h).
  • If approval is configured, a designated approver is notified and must approve before the role becomes active; some orgs allow self-activation with just MFA + justification for genuine break-glass scenarios.
  • The role auto-expires at the end of the window — no manual revocation step to forget.
  • Every activation is logged with who, when, why, and for how long — that audit trail is the actual point.

SEC-804SEV-2Defender for Cloud shows a "Secure Score" that dropped 8 points overnight. How do you investigate and prioritize?▶

Open the Recommendations blade filtered to "unhealthy" resources changed in the last 24h — new resources deployed without encryption, an NSG opened to 0.0.0.0/0, or an expired certificate are typical causes. Prioritize by the recommendation's actual risk weighting (not alphabetically) — Defender weights recommendations by exploitability and blast radius, so a public storage account with sensitive data outranks a missing tag every time. Fix the highest-weighted item first, then check whether it was a one-off manual change (points to needing Azure Policy to prevent recurrence) or came through IaC (points to a pipeline gate that should have caught it, e.g. a Checkov/tfsec scan).

SEC-805SEV-3What's the difference between Azure RBAC and Entra ID roles (like Global Administrator)?▶

Entra ID roles control the directory itself — creating users, managing app registrations, resetting passwords, configuring Conditional Access. Azure RBAC controls access to Azure resources — VMs, storage, resource groups, subscriptions. A Global Administrator does not automatically have access to Azure resources; that's a deliberate separation. The trap: someone assumes Global Admin equals "full access to everything," including subscriptions — it doesn't, unless that admin explicitly elevates access to manage Azure resources, which is itself a logged, auditable action.

SEC-806SEV-2A secret was accidentally committed to a Git repo and merged to main. What's your response?▶
  • Rotate first, clean up second — the secret is compromised the moment it's pushed, regardless of repo visibility; assume it's already been scraped. Rotate the credential in Key Vault / the source system immediately.
  • Purge it from Git history (filter-repo / BFG) — but understand this alone does not un-compromise it, it only stops future clones from carrying it.
  • Root-cause: why didn't a pre-commit or pipeline secrets-scanning gate (e.g. GitLab secret detection, gitleaks) catch this before merge — that gate is the actual preventive fix.

Pitfall

Spending the first 20 minutes scrubbing Git history while the live credential is still valid and exploitable. Rotation is always step one.

SEC-807SEV-2Design Conditional Access for a workforce that includes contractors on unmanaged devices, without blocking legitimate business travel.▶

Use risk- and context-based policies rather than a blunt country block: require compliant/hybrid-joined device or MFA for full-time employees; for contractors on unmanaged devices, require MFA plus restrict to browser-based access with no download (via Conditional Access App Control / session controls) rather than a native client with full sync. Layer in Identity Protection's sign-in risk score so an atypical-location sign-in triggers step-up authentication instead of an outright block — this handles genuine travel without exempting risky sign-ins.

entra-iddesign
SEC-808SEV-3When would you choose a user-assigned Managed Identity over a system-assigned one?▶

System-assigned is tied 1:1 to the resource's lifecycle — created and destroyed with it, simplest for a single VM. User-assigned is a standalone identity you create once and attach to multiple resources (e.g. every node in a scale set, or a Function App and its paired Logic App that both need the same downstream permissions) — useful when identity needs to persist independent of any one resource being recreated, or when several resources should share exactly the same permission set for easier auditing.

SEC-809SEV-2Leadership asks for a way to guarantee every new subscription automatically gets baseline security controls without relying on engineers remembering to configure them. What do you build?▶

Azure Policy initiatives (grouped policy sets) assigned at the management group level, not per-subscription — new subscriptions inherit the assignment automatically the moment they're placed under that management group. Use a mix of Deny (block non-compliant resources outright, e.g. public storage) and DeployIfNotExists (auto-remediate, e.g. attach diagnostic settings or enable Defender plans on anything that lands without them). This is the mechanism that makes a landing zone's guardrails self-enforcing instead of a checklist someone has to remember.

SEC-810SEV-2A Key Vault holds secrets used by 30 applications. How do you avoid it becoming a single point of failure or a blast-radius risk?▶

Don't use one vault for everything indiscriminately: segment vaults by sensitivity/environment/team (e.g. per application or per environment) so an over-broad RBAC grant or a compromised identity doesn't expose every secret in the estate — a single shared vault means one Key Vault Secrets User role handed out too widely equals blanket access. For availability, Key Vault is zone-redundant within a region by default on Premium/supported tiers; for DR, enable soft-delete and purge protection (mandatory for production) so accidental or malicious deletion is recoverable, and replicate critical secrets to a paired-region vault referenced by the DR runbook.
