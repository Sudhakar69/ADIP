Autoscaling: HPA vs VPA vs Cluster Autoscaler

A classic senior question: "traffic spiked and pods didn't scale — why?" You need to know which of three independent controllers was supposed to react.

ControllerScales whatTriggerCommon failure mode
HPA
Horizontal Pod Autoscaler		Replica count of a Deployment/StatefulSetCPU/mem % vs. requests, or custom/external metrics via metrics-server or KEDANo resources.requests set → HPA has nothing to divide against and refuses to scale

Vertical Pod Autoscaler		Requests/limits of a pod's containersHistorical usage recommendation engineRunning HPA and VPA on CPU for the same workload fight each other — VPA resizes, HPA reacts to the resize

i

Interview line that lands: "HPA answers 'do we need more copies,' VPA answers 'does each copy need more room,' Cluster Autoscaler answers 'do we have anywhere to put them.' They operate on different axes and can be combined carefully — never HPA+VPA on the same metric for the same workload.

Incident queue — Kubernetes

Click a ticket to expand. Each one mirrors a real "walk me through it" prompt.

K8S-101SEV-1A pod keeps restarting in CrashLoopBackOff. Walk me through your diagnosis.▶

Diagnose

  • kubectl get pods -o wide — confirm restart count and node placement.
  • kubectl describe pod <pod> — check the Events section and last termination reason/exit code.
  • kubectl logs <pod> --previous — the crashed container's logs, not the new attempt.
  • Exit code 1 = app error; 137 = SIGKILL, almost always OOMKilled; 143 = SIGTERM, graceful shutdown didn't finish in time.

Resolution

Match the exit code to a cause: bad config/env var → fix and redeploy; OOMKilled → raise resources.limits.memory or fix a leak; failing liveness probe → the app is up but the probe path/port/timing is wrong, not the app itself.

Pitfall

Candidates jump straight to "increase the memory limit" without reading --previous logs first — that's guessing, not diagnosing. Always show the evidence before the fix.

K8S-102SEV-2A new image was pushed but the deployment shows ImagePullBackOff.▶

Diagnose

  • kubectl describe pod Events will show the exact error: unauthorized, manifest unknown, or timeout.
  • Unauthorized → registry auth (imagePullSecrets) missing, expired, or not attached to the ServiceAccount.
  • Manifest unknown → tag doesn't exist (typo, or CI pushed to the wrong repo/tag).
  • Timeout → node can't reach the registry — check egress/firewall or private endpoint for ACR.

Resolution

For AKS + ACR, prefer az aks update --attach-acr (grants AcrPull via managed identity) over long-lived pull secrets — removes an entire class of "secret expired" incidents.

workloadsregistry
K8S-103SEV-1One node shows NotReady and its pods are stuck. What's your response?▶

Diagnose

  • kubectl describe node <node> — check Conditions: MemoryPressure, DiskPressure, PIDPressure, kubelet heartbeat age.
  • kubectl get events --field-selector involvedObject.name=<node> for kubelet/network plugin errors.
  • If it's a cloud VM, check the VMSS instance health in the Azure portal — could be an underlying host issue.

Resolution

If the node is unrecoverable within your SLA: kubectl cordon to stop new scheduling, kubectl drain --ignore-daemonsets --delete-emptydir-data to evict workloads safely (respecting PodDisruptionBudgets), then let Cluster Autoscaler or the node pool replace it. Never force-delete a node with stateful pods still attached to PVCs without confirming failover.

Pitfall

Draining without --ignore-daemonsets hangs forever since DaemonSet pods aren't meant to be evicted. Draining without checking PDBs can violate your own availability guarantees mid-incident.

K8S-104SEV-2CPU usage is high but HPA never scales the deployment. Why?▶

Diagnose

  • kubectl describe hpa — check the "current/target" metrics line; if it shows <unknown>, metrics-server isn't reporting.
  • Confirm the deployment has resources.requests.cpu set — HPA's percentage math is usage ÷ request, no request means no baseline.
  • Check maxReplicas hasn't already been hit, and that the node pool has room (Cluster Autoscaler may itself be the bottleneck).

Resolution

Set explicit requests, confirm metrics-server/Prometheus adapter is healthy, and separate the two questions "did HPA decide to scale" (control plane) from "could the cluster fit the new pods" (capacity).

autoscaling
K8S-105SEV-2A pod is stuck in Pending with a PersistentVolumeClaim.▶

Diagnose

  • kubectl describe pvc and kubectl describe pod — Events usually say exactly why: no matching StorageClass, zone mismatch, or quota exceeded.
  • In AKS, a classic case: the PVC's disk was provisioned in zone-1 but the pod got scheduled to a node in zone-2 (zonal Azure Disks aren't portable across zones).

Resolution

Use a StorageClass with volumeBindingMode: WaitForFirstConsumer so the disk is provisioned in the same zone the scheduler actually picks, instead of provisioning immediately and hoping.

K8S-106SEV-1Traffic to a Service returns intermittent 502s through the ingress. Where do you look?▶

Diagnose

  • Confirm kubectl get endpoints <svc> lists healthy pod IPs — a Service with a correct selector but zero endpoints is invisible traffic-wise.
  • Check the readiness probe: a pod can be Running but not Ready, and Ready is what gates Service endpoint membership.
  • Check ingress controller logs for upstream connection resets — often a mismatch between the app's actual listening port and the Service's targetPort.
  • Intermittent (not constant) 502s during deploys usually mean pods are removed from the endpoint list after traffic stops routing, not before — a missing preStop hook / graceful shutdown gap.

Resolution

Add a preStop sleep (or handle SIGTERM) so the pod keeps serving briefly while it's deregistered from the Service/ingress, and tune terminationGracePeriodSeconds. This is the single most common cause of "502s only during deploys."

Pitfall

Blaming the ingress controller first. In practice it's almost always readiness/endpoint timing, not the controller itself.

networkingtroubleshooting
K8S-107SEV-2Two pods in different namespaces can't reach each other after a NetworkPolicy rollout.▶

Diagnose

  • NetworkPolicies are additive and default-deny-once-selected: the moment any policy selects a pod, all traffic not explicitly allowed is denied.
  • Check both directions — ingress policy on the destination pod and egress policy on the source pod, both must allow the flow (if egress policies exist at all).
  • Cross-namespace traffic needs a namespaceSelector in the policy, not just a podSelector.

Resolution

Add an explicit allow rule with both podSelector and namespaceSelector (with a namespace label) for the calling service, and verify with a temporary kubectl run debug pod plus curl/nc rather than guessing from YAML alone.

networkingsecurity
K8S-108SEV-2A CI service account gets Forbidden: User cannot patch deployments. Fix it the right way.▶

Diagnose

  • kubectl auth can-i patch deployments --as=system:serviceaccount:ci:deployer -n prod reproduces the exact check.
  • Inspect the bound Role/ClusterRole and RoleBinding — missing verb, wrong resource, or bound in the wrong namespace.

Resolution

Grant least privilege with a namespaced Role + RoleBinding scoped to exactly the verbs needed (get, list, patch on deployments), not a blanket ClusterRoleBinding to cluster-admin just to unblock the pipeline.

Pitfall

"Just give it cluster-admin" is the answer that fails you in a security-conscious interview. Always narrate the least-privilege alternative even under time pressure.

securityrbac
K8S-109SEV-3A helm upgrade went out broken. How do you recover, and how could it have been caught earlier?▶

Diagnose

  • helm history <release> to see revisions, helm rollback <release> <revision> to revert immediately.
  • Post-recovery: helm diff upgrade (plugin) or --dry-run --debug in CI before every real upgrade to preview the rendered manifest diff.

Resolution

Roll back first, root-cause second — restoring service takes priority over understanding why in a live incident. Then add a CI gate: template-render + kubeval/conftest policy check + canary/staged rollout (Argo Rollouts or a manual weighted step) before full production.

K8S-110SEV-3How do you upgrade a production AKS cluster's Kubernetes version with zero downtime?▶

Diagnose & approach

  • Upgrade control plane first (managed by Azure for AKS), then node pools — never skip more than one minor version at a time.
  • Use a surge upgrade setting (maxSurge) so AKS adds new nodes on the target version before draining old ones, instead of upgrading in place.
  • Confirm PodDisruptionBudgets exist for every critical workload so the drain respects minimum availability.

Resolution

Blue/green the node pool: create a new node pool on the target version, cordon+drain the old one gradually, delete it once traffic has fully shifted. This avoids any in-place node reboot risk entirely and gives an instant rollback path (just stop draining).

K8S-111SEV-2When would you choose a StatefulSet over a Deployment, and what breaks if you get it wrong?▶

Answer

  • Deployment: identical, interchangeable, stateless replicas — pod identity doesn't matter, any replica can serve any request.
  • StatefulSet: stable network identity (pod-0, pod-1...), stable per-pod storage (PVC follows the pod on reschedule), ordered start/stop — needed for databases, Kafka, etcd-like systems.

Pitfall

Running a clustered database as a plain Deployment with a shared PVC: on rescheduling, two pods can mount (or fight over) the same volume, or lose their identity, corrupting cluster state. This is a favorite "why is this wrong" whiteboard question.

workloads
K8S-112SEV-2Nodes are running hot and you suspect noisy-neighbor pods. How do you confirm and contain it?▶

Diagnose

  • kubectl top pods --all-namespaces --sort-by=cpu for a quick view; Grafana/Prometheus for historical confirmation.
  • Check whether offending pods have limits set at all — without limits a pod can consume all available node CPU/memory.

Resolution

Enforce ResourceQuota at the namespace level and LimitRange for default requests/limits so no team can omit them; consider taints/tolerations or separate node pools to isolate genuinely bursty workloads from latency-sensitive ones.

K8S-113SEV-1etcd is corrupted / the control plane is unresponsive. What's the recovery plan?▶

Approach

  • On managed AKS, the control plane (including etcd) is Azure-operated — your job is opening a support case and failing over workloads, not restoring etcd yourself.
  • For self-managed clusters: etcd should have scheduled snapshots (etcdctl snapshot save); restore replaces the data directory on each member and requires a coordinated cluster restart.

Resolution

This question is really testing whether you know etcd is the cluster's single source of truth, so its backup cadence and restore drill needs to be tested regularly, not just configured and forgotten — and that on AKS this is Microsoft's responsibility under the shared responsibility model.

K8S-114SEV-3How do you secure a production cluster end to end — give me the layers.▶

Answer — layer by layer

  • Cluster access: Entra ID integration for kubectl auth, RBAC with least privilege, no shared static kubeconfigs.
  • Workload identity: Azure AD Workload Identity / Managed Identity instead of embedding cloud credentials as Secrets.
  • Network: default-deny NetworkPolicies, private cluster (no public API server endpoint) where possible.
  • Supply chain: image scanning in CI, signed images, admission control (e.g. Gatekeeper/Kyverno) to block unscanned or non-compliant images.
  • Runtime: Pod Security Admission (restricted profile), read-only root filesystem, non-root users, dropped Linux capabilities.
  • Secrets: external secret store (Key Vault via CSI driver) instead of raw Kubernetes Secrets at rest.
