Incident queue — CI/CD & Git

CI-201SEV-1A pipeline that worked yesterday fails today with no code changes. First three things you check?▶
  • Runner/agent health — did the runner pool change, get drained, or hit a version bump?
  • External dependency drift — base image, package registry, or a floating tag (:latest) that moved underneath you.
  • Pipeline/config changes merged by someone else, or a CI/CD variable that expired (token, secret rotation).

Resolution

Pin versions everywhere — base images by digest, tool versions explicitly — so "nothing changed" is actually true and the pipeline is reproducible.

CI-202SEV-2Design a pipeline that deploys to prod only after manual approval, but dev/staging are fully automatic. How?▶
# .gitlab-ci.yml (excerpt) deploy_prod: stage: deploy environment: name: production url: https://app.example.com when: manual rules: - if: '$CI_COMMIT_BRANCH == "main"' needs: ["deploy_staging"]

Combine when: manual with GitLab protected environments so only specific users/groups can click "deploy," plus branch rules so it can't fire from a feature branch.

pipelinerelease
CI-203SEV-1A bad deploy just went to production. What's your rollback strategy, and how fast can you execute it?▶
  • Fastest: re-run the previous successful pipeline's deploy job — the artifact/image already exists, no rebuild needed.
  • For Kubernetes: kubectl rollout undo or helm rollback as an even faster path if the pipeline re-run is slow.
  • For infra/config changes: revert the commit (not just redeploy old code) so the repo stays the single source of truth — avoids future drift between "what's deployed" and "what's in Git."

Resolution

State a target: "rollback executes in under 5 minutes because we redeploy a known-good, already-built artifact rather than rebuilding." That specific, measurable answer is what separates senior from mid-level here.

CI-204SEV-2Pipelines are slow — a build that used to take 4 minutes now takes 20. How do you speed it up?▶
  • Enable/verify layer caching (Docker build cache, GitLab cache: keyed by lockfile hash) — most slowdowns are cache invalidation, not raw compute.
  • Parallelize independent jobs (test splitting/matrix) instead of one long serial stage.
  • Check runner autoscaling — are jobs queued waiting for an available runner rather than actually running slow?
pipelineperformance
CI-205SEV-2Two engineers force-pushed over each other's work on a shared branch. How do you prevent this?▶
  • Branch protection: disallow force-push and direct commits to main/release/*.
  • Require merge requests with at least one approval and a passing pipeline before merge (merge trains for high-contention repos).
gitprocess
CI-206SEV-3Explain GitLab CI/CD variables and secret handling — how do you avoid leaking a secret in logs?▶
  • Mark sensitive CI/CD variables as Protected (only exposed on protected branches/tags) and Masked (redacted from job logs).
  • Prefer external secret stores (Key Vault, HashiCorp Vault) with short-lived tokens over long-lived CI variables where possible.
  • Never echo a variable, avoid set -x in scripts that touch secrets, and treat any accidental log exposure as a rotation event, not just a log cleanup.
securitypipeline
CI-207SEV-2You need the same pipeline logic reused across 30 microservice repos without copy-pasting YAML. How?▶

Centralize with GitLab CI/CD includes (include: project:) pointing at a shared templates repo, parameterized with variables per service. Update the template once, every consuming pipeline picks it up on next run — versus 30 repos drifting independently.

pipelinescale
CI-208SEV-1Merge conflict on a critical hotfix branch, production is down, you need this merged in the next 5 minutes.▶

Stay calm and don't shortcut safety: pull latest target branch, resolve conflicts locally with full context of both changes (not blind "accept theirs"), run the fast/critical subset of tests locally if the full pipeline is too slow, push, and let CI gate the merge. If genuinely blocked by a slow pipeline, use a documented emergency-deploy process (still logged, still reviewed after the fact) rather than disabling checks silently — traceability matters even in a fire.

processincident
CI-209SEV-3What's the difference between continuous delivery and continuous deployment, and which would you recommend here?▶

Continuous delivery: every change is automatically built, tested, and made release-ready, but a human decides when it actually ships (manual gate to prod). Continuous deployment: every change that passes the pipeline goes live automatically, no human gate. Recommendation depends on blast radius and rollback speed — teams with strong automated testing, feature flags, and fast rollback can safely run continuous deployment; regulated or high-risk-change environments usually keep a manual approval step for delivery instead.

process
CI-210SEV-2A GitLab runner has intermittent network failures pulling dependencies mid-pipeline. Long-term fix?▶

Add retry logic for network-flaky steps (GitLab supports retry: per job), but the durable fix is a local artifact/package proxy (e.g. a pull-through cache for npm/pip/Maven, or ACR as a pull-through cache for base images) so builds don't depend on the public internet's availability at all.

pipelinereliability
CI-211SEV-2How do you version and promote a build artifact across dev → staging → prod without rebuilding it each time?▶

Build once, tag with an immutable identifier (commit SHA or semantic version + SHA), push to a registry, then each environment's deploy job references that exact tag/digest. Promotion between environments becomes "point staging's deployment at the same digest that passed dev," never a rebuild — guaranteeing what you tested is exactly what ships.
